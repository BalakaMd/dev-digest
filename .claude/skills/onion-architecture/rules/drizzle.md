# Persistence ring — `modules/*/repository.ts`, `src/db`

The database is an implementation detail of one ring. Drizzle, `postgres`, the
schema and the row types are that ring's private vocabulary.

## Hard rules

- **Only a repository imports `drizzle-orm` or `db/schema`.** In a module, that
  means `repository.ts` and files under `repository/`. Nothing else — not the
  service, not helpers, not the route.
- **A repository takes `Db`, not `Container`**:
  `constructor(private db: Db) {}`. It has no adapters, no config, no logger
  decisions. It is the thinnest possible thing that can be swapped for a fake.
- **Public methods return contract types**, not `$inferSelect` rows. The mapping
  row → contract lives inside this ring. A `FindingRow` crossing into a service
  is the database dictating the domain's shape, and it is how a column rename
  turns into a fifteen-file diff.
- **Every method is workspace-scoped.** `workspaceId` is a parameter, joined or
  filtered in the query — never assumed, never held in module state. Scoping
  that lives in the service is scoping that the next caller will forget.
- **Transactions belong to the repository.** A service asks for an operation
  ("persist the review and its findings"); it does not open a transaction or
  pass a `tx` handle around. A `tx` in a service signature is the database
  reaching two rings inward.
- **No business rules in SQL.** A `where` clause that encodes a policy
  ("only findings above medium severity count") hides that policy from every
  test that does not have Postgres. Fetch, then decide in the service.

## Shape that already works here

`ReviewRepository` composes per-aggregate query modules — `repository/review.repo.ts`,
`run.repo.ts`, `pull.repo.ts` — behind one class with a stable public API. Copy
that when a repository outgrows a screen: split by aggregate, keep one facade.
Do not split by "queries" and "commands" unless the module genuinely has two
models.

## Migrations

Generated by drizzle-kit as `NNNN_<slug>.sql`, never hand-named and never edited
after they are applied; add a new one. They are not applied on boot — `pnpm
db:migrate` is explicit. Empty tables are expected in this repo: the schema runs
ahead of the features.

A migration is a ring-4 change. If a migration forces a change in
`reviewer-core`, stop and find the leak.
